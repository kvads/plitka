# Data model: помещения на «Плане» и «Вариантах»

Дата: 2026-10-12. Сохраняются ProjectDocumentV3, GraphSnapshot, RoomRecord и геометрический API. Новая часть дополняет [предыдущую модель](history/project-deletion/data-model.md); не меняет контракт удаления проектов.

## Страница

Runtime `PlanPage`: `plan | variants`. Stored `workflow.requestedStage` читает object/tile/rules/variants; UI отображает object как «План», остальные как «Варианты». При следующей записи нормализует в object/variants. Отсутствие face, selectedRoomId, результата или наличие pending не меняет страницу автоматически.

## RoomRecord

Существующие id, topologyKey, binding, name, material, rules, fieldInputs, acknowledgment, confirmed сохраняются. Новое поле:

| Поле | Ограничение |
| --- | --- |
| boundaryMemory | Необязательное в старом документе; после чтения null либо объект ровно с topologyKey/geometryKey |
| boundaryMemory.topologyKey | Строка из 64 строчных шестнадцатеричных символов: SHA-256 канонической внешней границы по направленным цепям |
| boundaryMemory.geometryKey | Строка из 64 строчных шестнадцатеричных символов: SHA-256 канонических точных координат внешней границы |
| name после переименования | После trim от 1 до 120 символов; пустое значение не заменяет прежнее |
| material | tile 50–2000 мм; grout 0–20 мм; только конечные числа |
| rules | gap 0–100 мм; threshold 1–1000 мм; angle от 0 включительно до 90 исключительно |
| fieldInputs | Исходный текст числового ввода сохраняется; пустой/нечисловой текст блокирует подбор выбранной комнаты |

ID остаётся ключом выбора, одинаковые имена допустимы. Новое имя — следующий свободный «Помещение N» выше существующих таких суффиксов, включая detached; переименование и удаление не перенумеровывают другие записи. Старое непустое имя сохраняется, старое пустое получает автоматическое имя при нормализации. Имя не входит в ключ результата.

## Идентичность границы

Memory описывает только внешний контур; отверстия участвуют в вычислительном fingerprint отдельно. Топологическая канонизация берёт цепи по направленным сегментам outer, сжимает подряд одинаковые chainId/направление, нормализует начало цикла и реверс с инверсией направлений. Координатная — удаляет повтор конечной точки, ровно коллинеарные промежуточные точки между соседями, нормализует циклический сдвиг и реверс; числа в мм без округления, -0 как 0. Hash input включает строку версии алгоритма `outer-v1`; сами значения хеша — 64 hex. Работа с координатами не меняет граф.

Порядок сопоставления одной актуальной проверки, после проверки generation/epoch/draftRevision:

1. Взаимно-однозначные attached записи по старому full topologyKey, затем outer memory topologyKey. Это сохраняет комнату при перемещении вершин и изменении отверстий.
2. Для оставшихся faces/records — взаимно-однозначное точное full topologyKey, затем outer topologyKey (в том числе detached).
3. Для оставшихся — взаимно-однозначный exact outer geometryKey. Это восстанавливает стену, нарисованную заново с новыми ID, при той же внешней форме.
4. Каждая ступень вычисляет кандидатов по всему оставшемуся набору до присваивания. Нет выбора по первому элементу, площади/перекрытию/близости или части общих стен. Неоднозначные faces получают новые записи, прежние сохраняются detached. Каждая face и record участвуют максимум в одной привязке.

У attached запись получает текущий полный topologyKey и обновлённую memory. У detached прежний topologyKey и memory замораживаются. Сохраняются id/name/material/rules/fieldInputs. Выбор исчезнувшей комнаты сбрасывается, страница остаётся прежней; после возвращения пользователь выбирает её на «Вариантах» без восстановления старого результата.

Старый документ: attached record заполняет memory только после однозначного совпадения с актуальной face. Для detached допустим источник confirmed.graph/boundary только при совпадении room.topologyKey с confirmed.topologyKey; иначе memory остаётся null, доступно лишь точное сопоставление сохранённого topologyKey. Не изобретать отсутствующую историю.

При explicit deleteRoom запись/память целевого помещения удаляются существующим purge, а у соседней разомкнутой комнаты сохраняются. Clear удаляет rooms/memory, его сессионный Undo восстанавливает. Удаление проекта удаляет весь активный документ по прежнему контракту.

## Готовность и результат (runtime)

`RoomReadiness`: no-selection | detached | validating | invalid | pending | ready. Автоматическая проверка должна соответствовать текущим draftRevision и basisKey/graph, иначе calculating запрещён. ready требует room.binding=attached, valid face и отсутствия pendingAffectsRoom. Для запуска дополнительно нужны materialReady и rulesReady.

`LayoutFingerprint`: projectId, roomId, face.dependencyKey, face.geometryKey, face.measurementKey, material, rules. Полевая ошибка, исчезновение face или изменение зависимостей инвалидирует результат независимо от равенства старого key после восстановления. Запуск/ответ/ошибка/finally также проверяют request generation, lifecycle epoch, текущий выбор и владельца. Старый результат не возвращается из кеша при повторном замыкании или смене выбора. Страница не входит в актуальность или generation: при смене только страницы готовый результат сохраняется, текущие optimize/layout завершаются в фоне. Ответ/ошибка для неизменных данных и выбора сохраняется без навигации; при возвращении показывается актуальный runtime state.

Результаты runtime, не добавляются в файл. Метаданные имени/адреса, zoom и формат подписи не инвалидируют результат. Legacy confirmed/acknowledgment остаются историческими снимками, не используются для ready/request/fingerprint и не обновляются как фиктивное согласие. restorePoint — сохранённый снимок, явное восстановление не равно подтверждению готовности.


## Владелец фонового расчёта

Runtime owner — открытый проект, а не активная страница. GraphWorkflow сохраняет results/loading/resultError при переключении plan/variants; скрытые панели не получают фокус. Текущая страница не входит в fingerprint/token. Для ручного layout дополнительно проверяются поколение запроса и принадлежность текущему ResultSet; старый finally не снимает loading более нового запроса.

| Событие | Результат и текущий запрос |
| --- | --- |
| Только смена страницы | accepted/pending/locked/selected/detail и ошибка сохраняются; запрос продолжается, навигации из callback нет |
| Success текущего optimize | Сохранить варианты и первый accepted, завершить loading; показать после возвращения |
| Success текущего layout | Принять новую раскладку/смещение, снять pending/loading; сохранить текущую страницу |
| Error текущего запроса | Сохранить параметры, accepted, pending ручного сдвига и ошибку, завершить loading; ошибочный/pending результат не экспортировать, повтор или явная отмена pending доступны на «Вариантах» |
| Смена выбранной комнаты или влияющих данных | Инвалидировать generation/результат; старые success/error/finally игнорировать |
| Импорт, clear/delete, выход из проекта | Применить lifecycle epoch/owner guards; фоновое продолжение между страницами не распространяется на закрытие проекта |

Единый расчёт fingerprint используется в ready-to-result guards, currentKey и live export check с самого перехода US1 на автоматическую готовность; confirmed не остаётся в одном из этих путей до US5. Метаданные, viewport и запись выбранной страницы не меняют generation. В частности, обычная documentRevision после autosave страницы не является причиной отмены расчёта неизменной геометрии.
