## Summary

Заменить четыре этапа двумя страницами на общем полотне: «План» для геометрии, «Варианты» для выбора помещения, его плитки, правил и явного запуска подбора. Убрать подтверждение размеров и помещения: готовность определяется актуальной проверкой графа. Сохранить подтверждения разрушительных операций. Замкнутые помещения получают видимые имена и возможность переименования. Временное размыкание скрывает имя на полотне, но сохраняет запись и настройки для однозначного восстановления. Подписи длин отображаются в м от 1000 мм, ниже — в мм; исходные значения и расчёт не округляются.

## Technical Context

**Language/Version**: существующие TypeScript 5.9.3, React 19.3.0, Python/FastAPI. Версии зависимостей не обновляются.

**Primary Dependencies**: React, SVG, существующие API геометрии/оптимизации и browser storage; новые пакеты не нужны.

**Storage**: `plitka-projects-v3`, прежний envelope и CAS/Web Locks. Необязательное `RoomRecord.boundaryMemory` расширяет v3. Старые файлы читаются; новые файлы не обязаны читаться старой версией приложения. Файл ≤2 МиБ, результаты расчёта не сохраняются.

**Testing**: только быстрые Chromium e2e, один worker, 15 с на тест / 5 с на действие, малые изолированные fixtures. При реализации допускается build/typecheck. Performance/load/stress/benchmark, pytest и отдельные unit/property/contract suites запрещены. При планировании тесты и сборка не запускаются.

**Target Platform**: браузер, мышь/клавиатура, 375/1440 CSS px. **Project Type**: React + FastAPI web application.

**Performance Goals**: количественных целей и замеров нет. **Constraints**: реальные мм/градусы, допуск условий 0,1 мм/°, отсутствие расчёта по устаревшему снимку, сохранение удаления/очистки/CAS и защиты от поздних ответов.

**Scale/Scope**: подбор для одного выбранного помещения, индивидуальные настройки всех комнат проекта; прежние лимиты графа. Новые серверные endpoints, коллективная работа, пакетный расчёт и изменение алгоритма раскладки не входят в объём.

### Последовательность последующей реализации

1. Подготовить малые fixtures и адресные e2e. В Foundation добавить типы/схему memory, page mapping и общий идемпотентный normalizer старых пустых имён до проверки совместимости US1; переиспользовать его для новых комнат US2.
2. В US1 ввести две страницы и ready/request по текущей face. Одновременно перевести все существующие проверки результата с confirmed на единый fingerprint: currentKey, effect устаревания и liveKey экспорта. Иначе первый подбор без confirmed остаётся несовместимым со старыми guards. До приёмки US1 убрать навигацию из optimize success и инвалидирование от смены только страницы; owner результата не размонтировать при переключении. US5 расширяет проверки гонок, а не впервые делает этот путь работоспособным.
3. В US2 реализовать канонизацию, memory и однозначное восстановление, имена/подписи; сохранить явное удаление RoomRecord. В US3 подключить formatter м/мм без изменения модели; в US4 завершить индивидуальные поля и их ошибки.
4. В US5 проверить общую актуальность success/error/finally для optimize и ручного layout, состояния accepted/pending/locked, детали/альтернативы/метрики и экспорт. Смена только страницы сохраняет состояние; смена выбранной комнаты, входных данных, импорт, clear/delete и выход из проекта отсекают старые ответы.
5. Выполнить адресные быстрые e2e и сборку при реализации; зафиксировать фактические результаты. Новые задачи/зависимости синхронизировать через speckit-tasks, не менять завершённую историю.

## Complexity Tracking

Отклонений gates нет. Дополнительная память границы нужна потому, что после удаления и повторного создания стены меняются ID цепей. Exact geometry fallback допускает восстановление только при взаимно однозначном совпадении; эвристик по близости и площади нет.
