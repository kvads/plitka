# Project file / storage: удаление и очистка

Дата: 2026-10-12. Формат остаётся `{format:"plitka-project",version:3,project:ProjectDocumentV3}`, UTF-8, ≤2 МиБ. Поддержка старых v3/v2/legacy, чистая миграция и ревизии импорта остаются по [базовому контракту](../history/vertex-safety/contracts/project-file.md). Настоящий документ уточняет только новый инкремент.

## Содержимое файла и совместимость

Файл содержит граф, fieldInputs, комнаты/настройки/подтверждения, pending, restorePoint, этап и viewport. Не содержит рассчитанных вариантов, acceptedPlacement, loading/errors, контекстных меню, выборов инструмента (включая rangeFirst/rangeSecond, пару концов и дугу), deletion/import preview, lifecycle epochs и Undo. Применённый диапазон сохраняется как прежний chainLength.target.range; его незавершённый выбор не меняет JSON. Поля координат остаются в формате независимо от отсутствия selected X/Y в интерфейсе.

Новые команды deleteRoom/deleteVoid/deleteConstraint разрешаются строгим union pending.command. Не менять существующие discriminator и не убирать addTemplate/unmarkVoid из чтения. Старый pending заготовки доступен для явного повторения/отмены даже при удалённых кнопках пресетов. Неизвестный discriminator или будущая версия → понятный отказ без изменения текущего проекта.

Копия снимков draft/basis/confirmed/restorePoint проверяется отдельно; геометрические ошибки вроде старого совпадения точек допускаются как черновик. Никакого ремонта при чтении. ID уникальны внутри снимка; одинаковые ID между снимками допустимы. JSON round-trip сохраняет raw десятичный ввод и конфликтующие условия.

## Сохранение успешного удаления

Перед сетевой командой сохраняется один pending basis+intent без частичного каскада. Успех устанавливает целый graph и связанные изменения RoomRecord в одном завершённом действии, очищает pending, даёт одну запись Undo. Техническая запись намерения до ответа не является отдельным Undo.

- deleteRoom удаляет целевую attached RoomRecord по topologyKey исходного документа. Записи соседей с исчезнувшей областью становятся detached по прежнему правилу; их настройки не переносятся на новую грань.
- deleteVoid/deleteElements пересвязывают комнаты через фактические faces; повреждённые void записи не сохраняются.
- deleteConstraint удаляет только условие и его raw поля. Освобождение остаётся отдельным fixed=false.
- Старые confirmed/restorePoint обычного удаления могут хранить историческую геометрию, но не разрешают актуальный расчёт/экспорт. Явное Undo или «Вернуть план к последнему подтверждению» по-прежнему отдельные действия; результат после них автоматически не оживает.
- На семантическом отказе нет частичного графа и успешного Undo удаления. При транспортной ошибке сохраняются basis/intent, текст ошибки и контекст объекта для явного retry/cancel.

## Очищенный ProjectDocumentV3

| Поле | Значение после clear |
| --- | --- |
| schemaVersion, id, name, address | Сохраняются |
| documentRevision | Текущая до записи, затем r+1 под CAS |
| plan.draftRevision | Предыдущая+1 |
| plan.draft | Пустые vertices/segments/chains/voids/constraints, fieldInputs={} |
| plan.pendingEdit, plan.restorePoint | null |
| rooms, selectedRoomId | [], null |
| workflow.requestedStage | object |
| viewport | Стандартные значения нового проекта |

Никакой beforeClear/backup/Undo snapshot не добавляется в файл или localStorage. Старые room materials/rules/confirmations отсутствуют, включая detached. Тот же проект остаётся в общей коллекции. Ключи других проектов и исторические v2/legacy резервные копии не удаляются. При наличии корректного v3 нет автоматического возврата из старого ключа; при повреждённом v3 действует прежний явный recovery с предпросмотром, не скрытый fallback.

Файл очищенного проекта импортируется как пустой существующий/новый проект по прежним правилам выбора импорта. После успешно сохранённой очистки reload/open не показывает Undo clear или восстановление из прежнего подтверждения.

## Undo clear

До закрытия проекта доступен один снимок pre-clear в runtime истории. Один Undo восстанавливает всё исходное содержимое: граф, размерный ввод, room settings, подтверждения, прежний restorePoint и pending намерение. Снимок не включает результаты/меню и не откатывает текущую documentRevision. draftRevision повышается, restored pending.targetDraftRevision переназначается. Сеть не запускается автоматически, явные retry/cancel остаются доступными. Разрешена новая validate восстановленного графа; она не выполняет intent.

Сохранить восстановленный документ стандартной записью. При этом старый pending вновь законно входит в JSON как восстановленные данные, а сам снимок Undo — по-прежнему нет. Этап variants заменяется rules, неготовая область — object. Нужен новый подбор перед экспортом.

## Очередь и конкурентная запись

`plitka-projects-v3` и Web Lock `plitka-projects-write` сохраняются. Под блокировкой перечитать коллекцию, проверить expectedRevision и заменить только целевой проект на revision+1. Без Web Locks по-прежнему отказ с объяснением; небезопасный обход не добавляется.

Планируемое расширение saveV3: необязательный предикат актуальности записи, проверяемый внутри lock перед CAS/записью. Явный результат `saved(document)` либо `skipped`; ошибки остаются ошибками. Существующие вызывающие без предиката сохраняют прежнее поведение через обёртку или overload.

- Clear/Undo clear синхронно повышают lifecycle/write epoch и ставят новый snapshot.
- Отменённая запись не публикует старый doc/onSaved/error/status; счётчики очереди уменьшаются корректно.
- Если setItem уже состоялся до clear, его revision принимается очередью, чтобы следующая запись не конфликтовала сама с собой; payload не возвращается в редактор/список.
- «Сохранено» относится только к последнему актуальному snapshot, успешно записанному под lock.
- Конфликт другой вкладки остаётся защёлкнутым; clear/Undo не сбрасывают conflict и не перезаписывают чужую ревизию.
- Ошибка quota/schema/access оставляет очищенный документ в памяти с «Не сохранено», экспортом и повтором в пределах прежних правил. До успеха reload может вернуть прежний сохранённый документ; UI не обещает обратного.
- Закрытие проекта уничтожает историю и делает сетевые callbacks неактуальными. Последний уже поставленный актуальный snapshot сохраняется по существующей гарантии выхода; не отбрасывать его только из-за unmount. Epoch защищает от устаревших снимков, live-owner — от публикации в закрытый UI.

## Guard для импорта файла

importV3 ожидает File.text; это асинхронный путь даже без HTTP. Начало чтения захватывает projectId/lifecycleEpoch/requestId и текущую локальную documentRevision. Перед публикацией кандидата, ошибки или изменением loading проверяются живой владелец, epoch и последний запрос чтения. После clear/Undo clear/закрытия прежнее чтение не открывает меню и не заменяет данные. Новое чтение инвалидирует старое. Перед подтверждением актуального preview сохраняется прежняя проверка ревизии; ревизия из файла не заменяет локальную.

G30i управляемо завершает чтение или ошибку после clear/Undo/закрытия. Отмена/сброс уже показанного preview без guard завершения чтения недостаточны.

## Guard для всех ответов

Любой callback graph/validate/legacy retry/deletion preview/layout/optimize/importV3 захватывает projectId и lifecycle epoch, затем прежние request generation/revision/input keys. Проверки выполняются после каждого await и перед success/error/finally. Для раскладки также roomId и dependency/input key. После clear и Undo clear старые ответы не устанавливают данные даже при полном совпадении восстановленных ключей. Abort допустим как оптимизация, но не заменяет guard.

Экспорт SVG/CSV и JSON проекта сейчас синхронный: проверка актуального принятого результата выполняется непосредственно перед download. После clear/Undo старый результат экспортировать нельзя; JSON самого проекта остаётся доступным по текущему состоянию. Задержанный ответ не может вернуть acceptedPlacement и тем самым снова разрешить экспорт. Новая асинхронность или сервер экспорта не нужны.
