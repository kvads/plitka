# Implementation Plan: Единое полотно и план помещений из связанных стен

**Branch**: `001-project-stages` (идентификатор функции, возвращённый setup-plan; Git-ветка не создаётся) | **Date**: 2026-10-11 | **Spec**: [spec.md](spec.md)

**Input**: спецификация после пяти уточнений о меню полотна, независимых вершинах, выбранном помещении, автоматических сочленениях и общей длине разделённой стены (FR-030–033). Повторное планирование учитывает одобренные исправления U1/I1/I2/C1: накопление условий, актуальность результатов, различие legacy/v2 и десятичный ввод.

## Summary

На странице проекта оставить одно постоянное SVG-полотно. Название/адрес, четыре этапа, инструменты, инспектор, ошибки, сохранение и результаты размещаются HTML-меню поверх полотна. На каждом этапе доступен только его набор инструментов и параметров; главное меню проектов остаётся отдельным экраном.

Заменить обязательный последовательный контур на плоский граф: независимые вершины, отрезки стен, общие узлы. Инструмент добавления вершин не соединяет точки автоматически; инструмент соединения создаёт стену между выбранными точками или от точки до стены. Точечные пересечения новой стены автоматически делят стены, сохраняют происхождение участков и образуют общие узлы. Из графа извлекаются ограниченные области; пользователь выбирает одно помещение для расчёта. Существующий раскладчик продолжает получать outline/holes в миллиметрах.

Исходная прямая стена после разделения остаётся связанной цепью участков с собственным общим размером. Ручной размер не заменяется измерением рисунка. Полный набор условий draft.constraints, намерение последней операции и подтверждённые помещения сохраняются раздельно в документе v3; v2 и legacy мигрируют без изменения координат и введённых условий.

## Technical Context

**Language/Version**: Python 3.12–3.14 (локальная проверенная ранее среда 3.14.4), TypeScript 5.9, React 19.2.

**Primary Dependencies**: существующие FastAPI/Uvicorn, Shapely 2, NumPy 2, установленная SciPy 1.18.1; Vite 7, lucide-react. Новая библиотека графов, WebGL, серверная БД и библиотека состояния не требуются. Существующий reducer остаётся единственным владельцем документа.

**Storage**: localStorage `plitka-projects-v3`, JSON envelope v3; v2/v1 остаются резервными источниками. Web Lock `plitka-projects-write`, свежая проверка documentRevision; без Web Locks — одна вкладка с обнаружением конфликтов без гарантии атомарности между вкладками.

**Testing**: только быстрые Chromium Playwright e2e на небольших планах, build/typecheck. FR-029 запрещает performance, нагрузочные, стресс-тесты, бенчмарки, pytest и неявный запуск запрещённых наборов. Один worker, action timeout 5 с, test timeout 15 с. В этой фазе тесты не запускаются.

**Target Platform**: существующее локальное веб-приложение, мышь/касание/клавиатура, ширина 375 и 1440 px. Список проектов остаётся прежним входом.

**Project Type**: frontend React + backend FastAPI, расширение существующего приложения.

**Performance Goals**: предварительное положение указателя локально; сервер получает только завершённые действия. Одна ограниченная попытка TRF, `max_nfev=200`; это предел поиска, не измерение скорости и не гарантия числа внутренних вычислений Якобиана. Нет новых количественных требований к задержке и нет performance-проверок.

**Constraints**: мм/°, независимость от масштаба; точность фиксированных размеров ≤0,1 мм/°, внутренняя цель 0,0001. Топологическая погрешность 1e-7 мм применяется только для вычисленного пересечения и переиспользования того же узла, не как допуск изменения замера. Полный запрос/файл ≤2 МиБ. Стабильные ID внутри снимка, запрет молчаливого исправления замеров, повреждённых файлов и старых ответов.

**Scale/Scope**: один план с несколькими помещениями; за один подбор — одно выбранное помещение. До 2100 вершин, 6300 участков, 6300 исходных стен, 12600 размерных условий в графе; до 20 явных отверстий. Область, передаваемая существующему planner, сохраняет предел 100 вершин на кольцо и 20 отверстий; большее помещение сохраняется в плане, но недоступно расчёту с объяснением. Координаты ±100000 мм, лимит раскладки 1600 ячеек проверяется при явном подборе. Эти ограничения ограничивают вход, не являются нагрузочным сценарием.

## Implementation sequence for task reconciliation

1. Ввести общие типы графа/v3 и fixtures; написать короткие e2e новых инструментов до реализации. Зафиксировать исходный дефект: add() и draw в ObjectStep ограничены `!c.closed`, состояния инструмента как самостоятельного понятия нет.
2. Создать graph validate/command, детерминированные split ID, явные и автоматические узлы, полную независимую проверку. Сначала сохранение намерения и безопасная отмена, затем исполнение транзакции; endpoint не зависит от старого ordered-contour solver.
3. Добавить извлечение областей, роли отверстий, устойчивый roomId и область влияния ошибок. Граф может быть незамкнутым; готовность выбранной комнаты не равна валидности всех элементов плана.
4. Ввести WallChain, общие длины, углы пары участков и solver затронутой системы условий. Прямые опоры/построения плюс TRF; запрет ослабления условий ради решения. Проверить сохранение 4000=1500+2500 и конфликтный ввод.
5. Реализовать v3 storage/import/migration, отдельное преобразование draft/confirmed/basis и legacy replay без потери старого pending. Полные проекты и legacy-ключи не удалять.
6. Перестроить страницу на постоянное полотно и панели инструментов/этапов. Проверить pointer-down/up, закрытие меню, исправление ошибки, числовые альтернативы и три независимые точки в уже существующем плане.
7. Подключить выбранное помещение к материалу/правилам/results и прежнему planner через адаптер. Пересчитать guards, dependencyKey и room identity; защитить поздние ответы сменой комнаты, ревизии или этапа.
8. Дополнить 5 существующих файлов быстрых e2e, выполнить build и разрешённый набор G/E. Новый функционал не готов, пока не проходят независимые вершины, T/X-сочленения, выбор комнаты, общий замер и полный перенос документа.

## State transitions after clarification

Размерный ввод сначала записывает весь актуальный набор условий и basis до действия, затем запускает solve. Отказ сохраняет координаты, но не откатывает ввод. Следующая размерная правка решает все накопленные условия; отмена pending восстанавливает её собственный basis. Структурные операции, move и legacyPending требуют явного retry/cancel перед новым действием с геометрией.

Изменение зависимого условия сразу делает результат stale и меняет поколение запросов. inputKey включает confirmed dependencyKey; повторное подтверждение и совпадение старого ключа не снимают stale. Только новый успешный подбор делает результат актуальным. Независимая правка временно приостанавливает экспорт до проверки области влияния, но не делает неизменную комнату stale.

Миграция legacy без условий начинает с объекта и проверки derived; v2 сохраняет действительное ack/fixed и последний доступный этап. Запятая и точка используют один NumberField для длины и угла.

## Verification and risks

Прежняя реализация прошла 46 быстрых e2e, затем 27 затронутых проверок; это исторические результаты, сохранённые в history/contour-v2/quickstart.md. Они не проверяют графовый редактор. При планировании код не изменён и новые проверки не запускались.

Основные риски: неверное наследование roomId при split/merge, потеря фиксации при разделении стены, ошибочная классификация отверстия как комнаты, клики сквозь меню, потеря pending при миграции. Для каждого предусмотрен отдельный короткий сценарий. Численный поиск остаётся ограниченным; невозможность найти форму — unresolved с сохранением ввода, не доказательство несовместимости. Контрольные простые фигуры обязаны сходиться.

## Complexity Tracking

Необоснованных нарушений нет. Граф, WallChain и room binding необходимы для прямо запрошенных разветвлений, общей длины и выбора помещения; модель одной последовательности точек больше не удовлетворяет требованиям. Новые сервисы и внешнее хранение не вводятся.

Уточнения анализа U1/I1/I2/C1 согласованы: draft хранит весь набор введённых условий независимо от pending; dimension retry/cancel сохраняет предыдущие конфликты, структурный pending не заменяется молча. Ключ результата включает зависимые условия; изменение fixed без смены формы требует нового подбора. Legacy без условий открывается на объекте, v2 сохраняет действительные подтверждения и доступный этап. T061/T073/T078–T079/T082/T089/T091 и короткие G08/G10/G12/G14 покрывают эти правила. Запрет performance-тестов остаётся без изменений.
