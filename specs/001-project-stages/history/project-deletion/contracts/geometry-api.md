# Geometry API: контекстное удаление и угол

Дата: 2026-10-12. Расширение API v3. Сохраняются существующие endpoints validate/command, schemaVersion=3, лимит 2 МиБ, строгие ссылки и лимиты GraphSnapshot. Полные прежние правила графа, solver, split и миграции: [базовый контракт](../history/vertex-safety/contracts/geometry-api.md). Этот документ приоритетен в части новых команд и каскада удаления.

## Существующие гарантии

- Backend stateless; миллиметры/градусы вычисляются из графа, viewport не передаётся.
- Некорректная форма входного JSON/CommandRequest или ссылки уже переданного GraphSnapshot → 422 с JSON error; превышение размера → 413; сбой → 500 с JSON error. Если корректный запрос создаёт ссылочно некорректный кандидат, отказ execute → 200, status=invalid, исходный graph и issues. Структурно допустимое, но несогласуемое размерное намерение → 200, status=unresolved, сохранённое условие и прежние координаты.
- Команды применяются к копии. При отказе нет addedIds/removedIds/splitMap изменений. Повтор одинаковых graph+command+commandId детерминирован; он не меняет внешнее хранилище.
- Прежние addVertex/connect/moveVertex/setLength/setAngle/setOrientation/releaseConstraint/reconcile/markVoid/unmarkVoid/addTemplate/deleteElements поддерживаются. addTemplate остаётся для старых pending/API и проверок; пользовательских кнопок заготовок нет.
- Общий запрет новых точных совпадений координат FR-034 остаётся, старые дефекты не ремонтируются. Численный EPS не равен экранному радиусу безопасности.
- Размерные команды сохраняют введённые условия при unresolved, не принимают несовместимые координаты. Допуски остаются 0,1 мм/°. Изменение связей/положения с незавершённым структурным pending требует retry/cancel; очистка является явным исключением на уровне документа.

## POST /api/plan/deletion-preview

Новый read-only запрос:
```ts
{
  schemaVersion: 3,
  requestId: string,
  draftRevision: number,
  basisKey: string,
  graph: GraphSnapshot,
  target:
    | {kind: "room", topologyKey: string}
    | {kind: "void", voidId: string}
}
```

Ответ:
```ts
{
  schemaVersion: 3,
  requestId: string,
  draftRevision: number,
  basisKey: string,
  status: "ready" | "invalid",
  target: DeletionTarget,
  impact: null | {
    impactKey: string,
    segmentIds: string[],
    vertexIds: string[],
    retiredChainIds: string[],
    constraintIds: string[],
    voidIds: string[],
    affectedRoomKeys: string[],
    disappearedRoomKeys: string[]
  },
  issues: Issue[]
}
```

На ready impact обязателен, на invalid равен null. Идентификаторы — существующие элементы basis, списки уникальны и отсортированы. Комнаты передаются через topologyKey; имена и roomId принадлежат клиентскому документу. disappearedRoomKeys — подмножество affectedRoomKeys. Изменённые ключи подтверждения при сохранённом topologyKey тоже включаются в affectedRoomKeys.

Предпросмотр находит ровно одну существующую грань с topologyKey комнаты либо существующее замкнутое отверстие с voidId. При отсутствующей/неоднозначной цели, неоднозначной границе или невозможности ссылочно корректного удаления — invalid с объяснением. Невалидность размеров и несвязанные старые дефекты сами по себе не запрещают корректное удаление: исправление повреждённого плана остаётся доступным. Повреждённый void с открытой границей можно убрать через unmarkVoid, без угадывания недостающих стен.

impactKey — SHA-256 канонического представления полного basis graph, типа/ID цели и рассчитанных последствий. Канонизация стабильна, не округляет координаты, учитывает constraints и fieldInputs. Это токен соответствия предпросмотру, не авторизация. basisKey остаётся непрозрачным эхом клиентского ключа; сервер не принимает его как доказательство правильности impactKey.

Предпросмотр не меняет документ, не создаёт pending, Undo или автосохранение. Клиент применяет его только при совпадении project/lifecycle epoch/draftRevision/basisKey и актуальной цели. До ответа нельзя подтвердить удаление.

## Новые варианты GraphCommand

```ts
{type: "deleteRoom", topologyKey: string, impactKey: string}
{type: "deleteVoid", voidId: string, impactKey: string}
{type: "deleteConstraint", constraintId: string}
```

Они идут в прежнем CommandRequest с schemaVersion, commandId, draftRevision, basisKey, graph. Новых полей ProjectDocument не требуется; union pending.command расширяется в серверной и клиентской схемах. Старые файлы/pending остаются читаемыми. Старый клиент, не знающий новые discriminator, не обязан открывать такой pending; текущий редактор не записывает неизвестный тип молча.

deleteRoom/deleteVoid повторно строят последствия из переданного graph и сравнивают impactKey. Изменившийся план требует нового preview/подтверждения, status=invalid и issue deletion_preview_stale. Отсутствующая цель даёт deletion_target_missing. Успех → status=applied, полный graph, faces/measurements/issues и обычные removedIds/addedIds/affectedChainIds; удалённые цепи/void/условия входят в removedIds. Новые остатки цепей — addedIds. Несвязанные геометрические issues могут оставаться при applied.

## Единый алгоритм удаления

1. Для комнаты объединить segmentId из face.outer и всех face.holes. Для отверстия использовать весь void.boundary. Не удалять dependencyIds и не расширять сегменты до целой исходной цепи.
2. Включить общие сегменты с соседями без исключений. Сохранить точные ID/координаты всех остальных сегментов и вершин.
3. Для комнаты/отверстия рассмотреть только концы удаляемых сегментов: удалить те, на которые не ссылается ни одна оставшаяся стена. Независимые точки не затрагивать.
4. Пересобрать затронутые цепи в непрерывные остатки с детерминированными ID. Незатронутые цепи сохранить. Удалить условия, ссылающиеся на удалённые vertices/segments или retired chains, включая range/angle/orientation и fixed=false. Не приписывать прежнюю полную длину остатку.
5. Любой void, потерявший хотя бы один участок boundary, удалить целиком; не сохранять обрезанный контур. Остальные кольца сохраняются. Удалить raw fields только удалённых условий/целей; unrelated raw fields сохраняются.
6. Проверить структурную целостность GraphSnapshot и проанализировать новый граф без solver. Пересчитать грани и зависимости до/после, собрать affected/disappeared. При исключении вернуть basis без частичного результата.

Тот же helper используется deleteElements. Его прежние vertexIds/segmentIds/acknowledgedConstraintIds сохраняются: удаление вершины включает инцидентные сегменты, обычное удаление стены не удаляет автоматически её отдельные концы. Прежде чем удалять условия, требуется их действующее acknowledgment. Старый UI-preview не может разрешить новые последствия после изменения basis. Исправление удаления повреждённого void применяется и здесь.

## Удаление и освобождение условия

deleteConstraint требует существующий constraintId, удаляет условие и точно связанные fieldInputs, не вызывает solver и не меняет координаты/стены. Все остальные, в том числе конфликтующие, условия сохраняются. Успех applied и removedIds=[constraintId]; отсутствующая цель invalid без изменения графа.

Это структурная атомарная команда, без предварительного удаления условия из видимого draft. Она может выполняться поверх сохранённого размерного намерения по существующим правилам; basis включает все уже введённые условия. Предшествующее структурное/legacy pending сперва явно отменяется/повторяется. На транспортной ошибке basis и intent сохраняются, меню остаётся. releaseConstraint отдельно сохраняет условие с fixed=false и прежнюю семантику pending.

## Диапазон длины: существующий контракт

Прямой выбор двух концов создаёт прежний setLength с target={kind:"chain",id:chainId,range:{startVertexId,endVertexId}}. Оба ID — разные существующие узлы одной цепи; клиент упорядочивает их по chain.segmentIds. Участки между ними образуют один непрерывный диапазон, value положительное. Обратный порядок выбора не создаёт другой target; для существующего диапазона переиспользуется constraintId по kind=chainLength, chainId и обоим каноническим концам независимо от fixed. Цель полной цепи без range остаётся отдельной. Сервер измеряет сумму участков диапазона и закрепляет его каноническое начало. До пары и применения числа запрос команды отсутствует. Неверный входной GraphSnapshot/форма запроса даёт 422. Корректный basis с новой командой, создающей неверную ссылку/порядок range, даёт прежний HTTP 200/status=invalid и исходный graph. Конфликт структурно корректного положительного размера — HTTP 200/status=unresolved с сохранением введённых условий. UI отсеивает неверную пару до отправки; проверки API остаются вторым уровнем. Отмена выбора — только runtime, без новой команды API.

## Контракт угла не меняется

```ts
{
  type: "setAngle", constraintId: string, vertexId: string,
  firstSegmentId: string, secondSegmentId: string,
  sector: "cw" | "ccw", value: number
}
```

Сегменты различны и имеют общий vertexId. Сектор измеряется от исходящего из узла луча первой стены к лучу второй в декартовой системе, допустимый ручной value строго между 0 и 360, кроме 180; вогнутые значения допустимы. 0°, 180° и 360° не принимаются как допустимые ручные условия; вычисленный 180° прямой стены остаётся derived. UI должен явно получить пару и сектор до отправки. Концы хранятся в исходном направлении стен; вычисление исходящих лучей не меняет направления сегментов. Порядок first/second и sector согласован при редактировании прежнего условия; эквивалентная обратная пара переиспользует существующий constraintId. Старые условия не переписываются при чтении. Сохраняется существующий серверный запрет ручного 180° и прежняя численная проверка, а не добавляется разрешение такого угла. Неверное конечное значение в прямом setAngle не становится структурным 422: это семантический отказ размерной команды (unresolved), исходные координаты и ошибочный intent/raw сохраняются по прежнему контракту. UI показывает адресную ошибку и не подтверждает геометрию; отображение derived 180° само по себе не создаёт setAngle.

## Клиентская атомарность и актуальность

Одна успешная команда удаления создаёт один законченный переход документа и один Undo. Сохранение pending до сети — запись намерения, не отдельное завершённое удаление. Успех одновременно устанавливает graph, bindings/rooms, очищает потерянные selection/menu/interaction и инвалидирует зависимые результаты. При invalid остаются basis и меню с ошибкой; не формировать успешный Undo удаления. При сетевой ошибке сохраняется pending для явного retry/cancel.

При deleteRoom удаляется именно целевая RoomRecord (по topologyKey соответствующего basis); потерявшие границу соседние записи становятся detached с прежними настройками по существующему правилу. Они недоступны для расчёта. Независимые комнаты сохраняют настройки. Подтверждение, меню и результаты утраченной грани не подменяются новой похожей гранью.

Очистка проекта не вызывает команду backend: она сбрасывает также клиентские настройки, pending и restorePoint. Любой поздний ответ preview/command/validate/layout/optimize и завершение импорта файла отклоняются после clear и после его Undo, даже при совпадении восстановленных ID/ключей. Экспорт готового результата выполняется локально и синхронно: он доступен только для текущего результата, отдельный export endpoint не добавляется.
