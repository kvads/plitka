# Research: окончательное удаление проектов

Дата: 2026-10-12. Область: FR-039/SC-018, US1.13–16. Исследованы действующие исходники; внешние библиотеки и сервисы не выбираются. Все вопросы проектирования разрешены. При повторном планировании A1/C1 сверены с действующим storage.ts и адресным фильтром тестов; независимая read-only проверка подтвердила совместимость без новой архитектуры. Исследование хранения отдельно проверено агентом read-only; код и пользовательские проекты не менялись.

## R1. Где происходит удаление

**Decision**: удаление — локальная операция каталога в `frontend/src/domain/plan/storage.ts`, без нового FastAPI endpoint. Новый `deleteV3(id, expectedRevision)` использует существующий Web Lock и одну запись оставшегося каталога.

**Rationale**: `Projects.tsx` и `storage.ts` хранят весь ProjectDocumentV3 локально; backend рассчитывает геометрию и не владеет проектами. Одна запись даёт целостный результат без промежуточного удаления частей проекта.

**Alternatives considered**: endpoint без серверной БД не удаляет фактические данные; серия операций по отдельным полям усложняет обработку сбоя; новая БД не входит в запрос.

## R2. CAS и конкуренция

**Decision**: под `plitka-projects-write` перечитать каталог и сравнить числовую documentRevision целевого ID с подтверждённой. Результаты deleted/alreadyMissing/conflict; conflict не записывает данные. Остальные проекты берутся из свежего каталога под lock. Обычный save существующего проекта никогда не переключается на expected=null после его исчезновения.

**Rationale**: saveV3 уже требует совпадения expected и текущей ревизии. Отсутствующий ID имеет null, поэтому ожидающее сохранение с числовой ревизией не создаст удалённый проект. Изменение другого проекта не является конфликтом удаления целевого.

**Alternatives considered**: сравнение только по имени опасно при совпадениях; удаление без CAS теряет новую версию; общий номер ревизии каталога создаёт лишние конфликты между независимыми проектами.

## R3. Legacy и пустой каталог

**Decision**: после последнего удаления записывать `{schemaVersion:3,projects:[]}`, не удалять ключ `plitka-projects-v3`. Существующие резервные ключи legacy/v2 остаются согласно действующему контракту; initializeV3 не читает их при наличии v3. Данные удалённого проекта не являются доступным активным документом или корзиной. Отдельного tombstone и новой версии схемы не требуется.

**Rationale**: initializeV3 мигрирует старые данные только при отсутствии v3. Сохранение пустого каталога исключает автоматическое повторное появление. Уточнение A1 прямо ограничивает полное удаление активным документом и состоянием редактора; стирание старых резервных копий браузера не требуется; скачанные файлы остаются у пользователя.

**Alternatives considered**: removeItem(KEY) возрождает старые проекты; отдельный реестр удалений требует атомарности нескольких ключей; удаление всех старых резервных ключей затронет чужие данные. Ручное повреждение/удаление каталога вне приложения не является штатным действием.

## R4. Подтверждение и рабочий черновик

**Decision**: в диалоге хранить ID, название, адрес, сохранённую expectedRevision и (для открытого редактора) localRevision. Снимок данных проекта в диалог/Undo не добавлять. Отмена до отправки ничего не меняет. На подтверждении проверить localRevision, приостановить изменения и новые записи, повысить lifecycle/write epochs; выполнить deleteV3 с исходной подтверждённой ревизией. Более новая сохранённая версия, включая успевшее собственное автосохранение, требует нового подтверждения, без автоматической подстановки ревизии.

**Rationale**: документ может измениться в памяти до автосохранения, поэтому одной documentRevision недостаточно. Короткая синхронная запись под lock не требует распределённой транзакции. Не нужно ожидать окончания всех запросов геометрии ради удаления.

**Alternatives considered**: автоматический retry с новой ревизией удалит неподтверждённые изменения; обязательное успешное сохранение черновика перед удалением делает операцию зависимой от прежней ошибки сохранения. Удаление не является clearProject и не попадает в историю отмены.

## R5. Терминальный lifecycle и ошибки

**Decision**: deleting блокирует команды и новые persist; успех или обнаруженное отсутствие переводит владельца в deleted, уничтожает runtime history/results/preview и закрывает редактор. Старые success/error/finally всех запросов и File.text игнорируются. Ошибка записи не очищает doc/history/pending/restorePoint, снимает deleting и показывает ошибку; epoch не откатывается. Возобновление сохранения — новым актуальным snapshot по прежнему CAS, без воспроизведения старой очереди или pending-команд. Конфликт остаётся защёлкнутым по прежним правилам; разрешение требует явного действия.

**Rationale**: useGraphProject сохраняет последнюю актуальную запись после обычного unmount. Для удаления нужен отдельный guard, но обычный выход в список не должен потерять сохранение. Имеющиеся epochs уже защищают graph/validate/legacy/preview/optimize/layout/import; расширяется причина прекращения работы, а не сеть.

**Alternatives considered**: alive-only guard ломает обычное сохранение при выходе; очистка документа до setItem теряет черновик при отказе; возврат epoch назад разрешает старые ответы.

## R6. Другая вкладка и маршрутизация

**Decision**: Projects слушает storage для v3, перечитывает rows и закрывает отсутствующий открытый ID с сообщением. useGraphProject также трактует отсутствие как terminal missing, а более новую существующую ревизию — как конфликт. Локальный успех обновляется явным callback, поскольку storage не приходит в записавшую вкладку. Старый URL получает состояние «Проект не найден» с возвратом к списку. Запоздалый onSaved не вставляет удалённую запись.

**Rationale**: сейчас Projects слушает только hashchange, а hook игнорирует отсутствующий документ. Обе точки требуют изменения. Перечитывание вместо применения e.newValue избегает возврата устаревшего каталога при нескольких событиях.

**Alternatives considered**: polling не нужен; BroadcastChannel дублирует storage; принудительное перемонтирование редактора при любой записи другой вкладки потеряет локальный черновик.

## R7. UI и приёмка

**Decision**: один переиспользуемый DeleteProjectDialog для списка и меню, на основе текущего CanvasDialog с явным возвратом фокуса. Первоначальный фокус на «Отмена», блокировка фона, имя/адрес и явное отсутствие отмены. После успеха фокус на заголовок списка; при отмене на исходную кнопку. Импорт из списка сохраняет имеющееся создание UUID. По уточнению C1 все новые тесты удаления в трёх целевых файлах используют префикс `delete project `, включая T181/D05/D06: общий фильтр запуска должен охватывать ошибки и конфликты наравне с успешным удалением.

**Rationale**: уже есть подтверждение очистки и focus trap; требуется адаптация для списка без SVG. Быстрые e2e с настоящим localStorage/Web Locks и двумя страницами одного browser context проверяют сценарии без нагрузочных тестов.

**Alternatives considered**: window.confirm не даёт управляемого оформления и состояний ошибки; корзина/Undo отклонены пользователем; отдельная библиотека модальных окон не нужна.
