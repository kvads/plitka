**Branch**: `001-project-stages` (идентификатор функции; Git-репозитория/созданной ветки нет). **Date**: 2026-10-12. **Spec**: [spec.md](spec.md).

**Input**: FR-039, SC-018, US1.13–16; подтверждён вариант A — окончательное удаление с подтверждением, без Undo/корзины. Phase 0–1 и реализация завершены 2026-10-12: 38 новых быстрых e2e, 7 адресных регрессий и build прошли. T047–T176 остаются завершённой историей. Сформированы 25 новых задач T177–T201. План повторно синхронизирован с принятыми уточнениями A1/C1 от 2026-10-12; задачи T177–T201 выполнены без переоткрытия прежних.

## Summary

Добавить «Удалить проект» в список и меню открытого проекта. Один диалог называет проект и адрес, предупреждает об отсутствии отмены и сначала фокусирует «Отмена». После успешной записи активный документ проекта удаляется целиком из каталога, состояние редактора очищается и редактор закрывается; остальные проекты сохраняются. Последний проект оставляет пустой список с созданием нового.

Удаление выполняется в текущем localStorage под тем же Web Lock, что автосохранение. Сравнение подтверждённой ревизии защищает новые изменения. Пустой каталог v3 сохраняется, чтобы старая миграция не вернула проекты. По уточнению A1 старые резервные копии для миграции остаются без изменений, но не служат активным документом или корзиной и автоматически не восстанавливаются. Формат документов не меняется, новый backend endpoint и tombstone не нужны. Редактор получает терминальное состояние удаления, которое блокирует старые записи и ответы; существующая гарантия сохранения при обычном выходе остаётся.

## Technical Context

**Language/Version**: TypeScript 5.9.3, React 19.3.0; Vite 7.3.7 и Playwright 1.64.0 по текущему lockfile. Существующий Python/FastAPI backend не меняется.

**Primary Dependencies**: существующие React, Web Storage, Web Locks, storage events, CanvasDialog; без новых пакетов или обновления зависимостей.

**Storage**: `plitka-projects-v3`, envelope `{schemaVersion:3,projects:[...]}`, CAS по documentRevision, lock `plitka-projects-write`. Скачиваемый файл остаётся v3, ≤2 МиБ. Нет новой схемы/БД/серверного хранения.

**Testing**: только быстрые Chromium e2e на малых изолированных fixtures, 1 worker, 15 с на тест/5 с на действие; build/typecheck при реализации. Performance/load/stress/benchmark, pytest и отдельные unit/property/contract suites не запускать. Во время этого планирования ничего из перечисленных проверок приложения не запускалось.

**Target Platform**: существующее браузерное приложение, 375/1440 CSS px, мышь/клавиатура; несколько вкладок одного origin. **Project Type**: React + FastAPI web application.

**Performance Goals**: количественных целей/замеров нет; операции по пользовательскому действию, без polling. **Constraints**: окончательное одиночное удаление, отсутствие Undo и корзины; no silent retry на новую ревизию; сохранность других проектов, старых форматов и обычного автосохранения.

**Scale/Scope**: одна запись каталога за удаление; список, меню редактора, общий диалог, storage/lifecycle. Работа с большими каталогами и массовое удаление не входят в объём. Геометрические лимиты и алгоритмы не затрагиваются.

## Phase 0 — completed

[research.md](research.md) фиксирует решения R1–R7. Исследование исходников подтвердило: saveV3 уже защищает отсутствующую запись числовым expected; initializeV3 опасен только при удалении самого ключа; Projects не слушает storage, а hook игнорирует отсутствующий документ. Эти недостатки включены в план. Рассмотрены и отклонены tombstones, новый endpoint, автоподстановка новой ревизии, корзина и блокировка обычного сохранения при unmount.

### Последовательность для последующей генерации задач

1. Подготовить малые fixtures и новые быстрые e2e с префиксом `delete project ` во всех трёх целевых файлах, включая D05/D06 в T181 (C1), для удаления, отказов и двух вкладок; первоначальные новые функциональные проверки должны выявить отсутствие реализации.
2. Добавить typed deleteV3 под существующим lock и CAS, исходы deleted/alreadyMissing/conflict; сохранить пустой каталог и остальные документы. Проверки API здесь являются браузерными e2e хранения, отдельный contract suite не нужен.
3. Добавить временный deleting и terminal missing guards в hook; согласовать write epochs, все async callbacks и обычный unmount. При отказе сохранить текущий документ; не возвращать старые поколения или очередь.
4. Подключить единый диалог к списку и ProjectMenu, блокировку повторного подтверждения/фона, явное новое подтверждение при конфликте, управление фокусом.
5. Синхронизировать storage events, удаление открытой копии другой вкладки, локальное обновление rows, старые ссылки и новое ID при явном импорте.
6. Выполнить адресные быстрые e2e, затем build/typecheck. Согласовать фактические результаты; прошлые проверки не объявлять приёмкой этого инкремента.
