# Project file и локальное хранение v3

Целевой формат — полный ProjectDocument из [data-model.md](../data-model.md), JSON UTF-8 ≤2 МиБ на файл/запрос. Экспорт не содержит вариантов, SVG/CSV, runtime errors, запросов или Undo; содержит граф, raw fields, pending, confirmed, restorePoint, комнаты и их параметры. Экспорт проекта с незавершённым графом разрешён. Экспорт раскладки требует актуального acceptedPlacement.

## Формат и проверка

Файл: `{format:"plitka-project",version:3,project:ProjectDocument}`. schemaVersion документа равен 3. Проверка по строгой схеме: конечные числа, лимиты, уникальность ID внутри каждого снимка, целостность ссылок, tagged union pending. Один ID может повторяться в draft/basis/confirmed/restorePoint. Неизвестную будущую версию и структурно повреждённый файл отвергать без изменения текущих данных. Геометрически незавершённый/противоречивый draft допустим; его нельзя исправлять при чтении.

Импорт сначала показывает название/адрес, версию, наличие draft/pending и предполагаемую замену. Подтверждённая пользователем замена проверяет свежую локальную ревизию под блокировкой; изменение с момента предпросмотра → конфликт, без записи. При замене сохраняется локальный ID проекта; при создании из файла назначается новый ID, внутренние ID графа сохраняются. Для нового импортированного проекта documentRevision=0, для замены r→r+1 независимо от ревизии файла. Поддерживаются v3, существующий envelope v2 и прежний bare Project через последовательные адаптеры. Формат v2 читать по фактической старой схеме, не переименовывать поля предположительно.

## Миграция v2

Миграция — чистое преобразование без сетевых запросов/solver, округления, автоматического подтверждения или изменения локальной ревизии. ID проекта, имя/адрес, координаты, сырые поля, fixed/value, материал/правила сохраняются. Каждое состояние draft, confirmed и pending basis преобразуется отдельно.

1. Каждый прежний vertex сохраняет ID. Каждый старый wall становится Segment с тем же ID и своей исходной WallChain. ID цепи детерминированно выводится из projectId+старого wallId с отдельным namespace и проверкой коллизий. Одинаковый wall во всех снимках получает одинаковую цепь. Замыкающую стену создавать только если она существовала в исходном снимке.
2. Контуры holes сохраняют роль явного void и прежний ID. Наружный контур не становится отверстием. Старые неполные контуры не замыкать.
3. Размер старой стены становится chainLength с прежними constraintId/value/fixed. Угол переносится в её конечный узел и пару исходной/следующей стены: при обходе CCW сектор от обратного луча исходной стены к следующей — cw, при CW — ccw. Сохраняются рефлексные углы. Ориентация первой стены переносится на её цепь.
4. Неоднозначное старое условие не удалять: `legacyUnbound` сохраняет оригинал и объяснение, блокирует зависимое подтверждение до исправления. Это состояние допустимо только из миграции.
5. Создать одну RoomRecord с прежними параметрами. Валидная старая область получает вычисляемый из происхождения стен topologyKey; неполная — detached. После серверной проверки связывать только по точному однозначному ключу. Не выбирать другую комнату по центроиду или похожей площади.
6. Старое acknowledgment переносится только после проверки старых ключей по старым правилам и эквивалентности преобразованного confirmed. Затем пересчитываются новые ключи и сохраняется факт прежнего явного подтверждения. При расхождении сохраняются данные, но подтверждение не считается действующим. Последующая проверка не создаёт согласие пользователя.
7. pendingEdit преобразуется в `legacyV2`, сохраняя точные operation, basisGeometry, draftGeometry, targetDraftRevision. Reload не запускает его. Явный повтор использует старый geometry endpoint, преобразует ответ и проверяет граф новым endpoint; все стадии защищены токеном. Отмена восстанавливает преобразованный basis. Нельзя угадывать эквивалент графовой команды и терять намерение.
8. Legacy без условий открывается на объекте с вычисленными размерами для явной проверки. V2 сохраняет действительные fixed/ack и последний доступный этап; миграция сама по себе не требует нового согласия. restorePoint берётся из прежнего confirmed; старые результаты не переносятся. Этап variants понижается согласно guards выбранной комнаты.

Если преобразованный документ превышает лимит или не проходит структурную проверку, исходник остаётся доступен для скачивания; миграция не пишет частичный документ. Исходный v2 snapshot в legacyPending также проверяется по старой схеме и входит в общий лимит файла.

## localStorage и конкурентность

Новый ключ `plitka-projects-v3` со значением `{schemaVersion:3,projects:ProjectDocument[]}`, существующие v2/v1 ключи остаются резервной копией. Сохранять фактическую структуру коллекции через явный адаптер. Загрузка выполняется через асинхронную инициализацию: взять существующий общий Web Lock `plitka-projects-write`, перечитать ключи, выбрать v3 при наличии, иначе мигрировать v2/legacy и записать целиком после проверки. Не удалять источники и не повышать documentRevision при автоматическом переносе.

Повреждённый существующий v3 не разрешает незаметный fallback к старым данным. Показать ошибку и явное восстановление резервной копии с предпросмотром. Изменение v2 другой старой вкладкой после миграции обнаруживать через storage event/проверку исходной подписи: предупреждать о расхождении, не сливать автоматически.

Запись текущего проекта под тем же Web Lock перечитывает коллекцию и expectedRevision; обновляет только целевой документ с r+1, сохраняя остальные. Отказ quota/доступа/схемы не означает «Сохранено»: документ в памяти остаётся доступен для скачивания/повтора. Без Web Locks текущая реализация сообщает об ограничении и отказывает в записи; небезопасный fallback одной вкладки не используется.

Автосохранение не ждёт solver: pending basis+intent сохраняются первыми. После ответа пишется только актуальный результат. Локальная storage revision и geometry draftRevision различны. Перемещение камеры/название/адрес не меняют geometryKey и не инвалидируют расчёт. Переход к другому проекту не применяет оставшийся ответ к открытому документу.

## Восстановление и комнаты

Разделение/слияние области оставляет прежнюю RoomRecord detached со всеми настройками и confirmed; новые области получают новые записи без неявного переноса подтверждений. Простое сочленение, не меняющее область, сохраняет roomId. JSON round-trip обязан сохранять оба случая.

«Вернуть план к последнему подтверждению» восстанавливает весь restorePoint после предпросмотра затронутых комнат. Восстановление только одной границы поверх общего графа запрещено. Параметры RoomRecord не удаляются; bindings пересчитываются, неподтверждённая выбранная область возвращает пользователя к этапу объекта.

`draft.constraints` сохраняет все применённые числовые условия, в том числе конфликтующие; pending описывает лишь последнее действие. После второго изменения другого размера первый конфликтующий ввод не теряется. Отмена второго действия, включая после reload, восстанавливает его basis с первым условием. Preview связей/координат не выдаётся за принятую геометрию.

Применение ответа сервера не заменяет текущие draft.fieldInputs старым текстом basis. Полный JSON сохраняет введённый текст (включая десятичную запятую) независимо от числового представления условий. Undo после успешной операции доступен в runtime истории; после reload отменяется сохранённый pending через его basis.


## Инкремент FR-034: старые совпадающие вершины

Формат v3 остаётся прежним. Совпадение координат не является структурной ошибкой импорта: все вершины, стены, условия, raw fields и отдельные снимки сохраняются с исходными ID и координатами. При открытии не объединять вершины, не удалять нулевую стену и не переписывать геометрию. Исходные источники v2/legacy также не исправляются.

Зона безопасности, preview, CoincidentPair, сообщения и DiagnosticSelection не сериализуются. Reload/import вызывает диагностику с прежним разделением draft/confirmed, не автоматическую команду ремонта. Ни одинаковые точки, ни удалённая из диагностики каскадная карточка не дают автоматического подтверждения помещения.

Undo/cancel/restore могут вернуть исторический снимок с дефектом: сохранность данных имеет приоритет над запретом создания нового дефекта командами. Явный повтор legacyPending проверяет преобразованный кандидат перед сохранением; отказ не теряет intent или basis. Текущий пользовательский проект не является тестовой фикстурой и не меняется при реализации этих проверок.
