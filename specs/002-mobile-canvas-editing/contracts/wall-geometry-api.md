# Contract: команды геометрии стен

Существующий `POST /api/plan/command` принимает граф v4, команду, `basisKey`, `commandId` и сведения о ревизии; возвращает граф, статус, проблемы, область стен и производные комнаты. Единицы координат и толщины — мм. Текущие `drawWall` и `setWallThickness` сохраняют прежние поля и смысл.

## Новая команда

```json
{
  "type": "nudgeWallHandle",
  "chainId": "wall-chain-id",
  "handle": "start",
  "axis": "x",
  "direction": 1
}
```

`handle` допускает `start`, `center`, `end`; `axis` — `x` или `y`; `direction` — `-1` или `1`. Один вызов смещает выбранную точку ровно на 1 мм по указанной оси; произвольный `deltaMm` клиент не задаёт. `chainId` указывает на WallChain, а не на отдельный Segment, потому что стыки делят одну стену на несколько сегментов. Неизвестная цепь, неверная форма или значение поля отклоняются существующим способом проверки запроса.

Для `start`/`end` сервер меняет только соответствующую крайнюю вершину цепи на 1 мм. Все внутренние вершины и противоположный конец остаются на месте; если через неподвижные внутренние вершины новая ось не может остаться прямой и упорядоченной, сервер отклоняет всю команду. Для `center` сервер переносит все вершины выбранной цепи на 1 мм, включая внутренние стыки. Разделяемые вершины стыков остаются едиными ID; присоединённые стены меняют положение своих затронутых концов, а их дальние концы остаются на месте. Если любая присоединённая цепь не может остаться валидной, сервер отклоняет всю команду, не искажая её молча.

Перед `status: applied` обязательны проверка порядка и положительной длины сегментов, прямолинейности всех цепей, топологии, ограничений, пересечений, совпадения вершин и физического наложения всех затронутых стен. Ответ `affectedChainIds` содержит каждую стену, координаты которой изменились, включая присоединённые через общий стык. На невозможное изменение сервер возвращает `status: invalid`, исходный `graph` и понятную причину в `issues`. Пользовательский `issues[].message` не содержит числовых координат и списков вершин; код проблемы и структурированные идентификаторы могут сохраняться для проверки и выбора на полотне. Например, `coincident_vertices` объясняет совпадение точек стены без пары X/Y. Никакой части смещения не сохраняется. Клиент не оставляет блокирующее `pendingEdit` после такого ответа и допускает следующую стрелку. Повторный `commandId` сохраняет существующую идемпотентность; проверка ревизии и `basisKey` действует как для других команд.

## Существующая физическая стена

`drawWall` принимает осевую линию и толщину новой стены (по умолчанию 100 мм). Ось доходит до топологического стыка с первой встреченной стеной; видимая новая область подрезана у первой физической грани. Область всех стен — объединение, поэтому стык считается один раз. Продолжение через стену или недопустимое наложение отвергается атомарно. `setWallThickness` меняет толщину цепи; допустимая толщина, сделавшая полезный контур комнаты непригодным, всё равно применяется, а комната получает причину невалидности и блокировку расчёта плитки.

Ответ сохраняет `graph.chains[].thicknessMm`, объединённую `wallArea`, `faces[].axisPolygon`, полезный `faces[].polygon`, `areaMm2`, `dependencyKey`, `geometryKey` и `validation`. Непригодный полезный контур возвращает `polygon: null`, `areaMm2: null` и причину, без выбора одного из нескольких компонентов. Идентичность комнаты определяется осевым контуром и не меняется от одной только толщины.

## Числовой контракт

Версия ответа геометрического API остаётся `schemaVersion: 4` и не совпадает с версией локального документа v5. Во входной команде предметные параметры (координаты, толщина, длина, угол) имеют шаг 0,1 мм или 0,1° по смыслу поля; значения с большей точностью отклоняются. Служебные идентификаторы и целочисленные ревизии не квантуются.

Сервер может вычислять пересечения и решать ограничения с более высокой промежуточной точностью. Перед формированием ответа новые общие вершины согласованно приводятся к десятичной сетке 0,1 мм. Клиент выбирает цель перпендикулярной направляющей как ближайшую каноническую точку к идеальной до отправки команды: отклонение от неё не более 0,08 мм, от соответствующей 100-миллиметровой отметки не более 0,1 мм, от прямого угла не более 0,1°. Сервер применяет к полученной точке обычную проверку команды и после приведения повторяет проверки стыков, порядка и прямолинейности цепей, размерных условий, коллизий и физического наложения. Производные полигоны, измерения, площади и ключи зависимостей формируются из итогового графа, а предметные числовые поля ответа имеют не более одного десятичного знака в своих единицах; `areaMm2` выражено в мм². Ключи остаются детерминированными для повторной команды. Если правка невалидна после приведения, сервер возвращает `status: invalid`, исходный граф и причину; частичного результата нет.

## Локальный проект

В каталоге `plitka-projects-v5` хранятся только новые документы `schemaVersion: 5`, прошедшие проверку числового инварианта во всех вложенных снимках графа и комнатах. При первом создании v5-каталога приложение удаляет прежние ключи v1–v4 и не переносит их проекты. Каждый последующий запуск повторяет удаление оставшихся старых ключей под блокировкой, не очищая валидный v5. Форматы файлов v1–v4 не импортируются; изменение этой политики потребует отдельного решения пользователя. Отказ записи нового каталога не удаляет старые данные.
