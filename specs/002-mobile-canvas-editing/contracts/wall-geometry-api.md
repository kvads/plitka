# Contract: команды геометрии стен

## Геометрия v5 для физических стен — текущий контракт

Новый клиент отправляет `POST /api/v5/plan/validate`, `POST /api/v5/plan/preview`, `POST /api/v5/plan/command` и `POST /api/v5/plan/deletion-preview` с `schemaVersion: 5`. Все маршруты используют один `PhysicalGraphV5` из [data-model.md](../data-model.md). Старые `/api/plan/*` с осевой схемой v4 остаются без изменения для открытых вкладок предыдущей сборки; текст ниже в разделе «Геометрия v4» описывает только их.

`validate` принимает пустой граф и уже сохранённый физический граф без новой команды и без изменения ревизии. На фундаментальном этапе до `drawWall` обязателен полный ответ для пустого графа и одной сохранённой изолированной стены: `wallArea` строится из сохранённых `corners[4]`, `faces` и `openJointAngles` пусты, если замкнутой комнаты и стыка нет. Полная проверка контактов, комнат и измерений для графа со стыками добавляется тем же маршрутом в US4. Ошибка формы или доступной на данном этапе топологии возвращает `invalid` с исходным графом; новый клиент не получает успешный ответ с фиктивными комнатами.

```json
{
  "schemaVersion": 5,
  "commandId": "stable-request-id",
  "draftRevision": 3,
  "basisKey": "canonical-physical-graph-key",
  "graph": { "walls": [], "junctions": [] },
  "command": {
    "type": "drawWall",
    "drawnEdge": [{ "x": 0, "y": 0 }, { "x": 1000, "y": 0 }],
    "side": "left",
    "thicknessMm": 100
  }
}
```

`drawWall` принимает две точки **выбранного видимого края** в порядке проведения, `side: left | right` и `thicknessMm` (по умолчанию 100 мм только при отсутствии поля). Для телефона и ПК тело одинаково. Сервер строит четыре упорядоченных физических угла, сохраняет их в `graph.walls[].corners` и возвращает выбранный край/сторону/толщину без зеркалирования при внутреннем изменении порядка вершин. Входные точки и толщина имеют шаг 0,1 мм; допустимая толщина — от 0,1 до 100000 мм. Нулевая длина, невалидная толщина, самопересечение, ошибочная ориентация и невозможный стык отклоняются.

`PhysicalWallV5` в ответе содержит `id`, `drawnEdge`, `side`, `thicknessMm`, `corners[4]` и стабильные ссылки на `junctions`. Четыре точки имеют шаг 0,1 мм. После вычисления второго края с полной промежуточной точностью сервер приводит углы согласованно и проверяет фактическую ширину у обоих концов с допуском 0,1 мм, параллельность и простой полигон. Углы не принимаются как четыре свободных редактируемых значения: при каждой команде сервер выводит их из выбранного края, стороны и толщины, исключая накопление ошибки.

Каждый элемент `graph.junctions` имеет форму `{"id":"junction-id","participants":[{"wallId":"wall-a","edge":"endCap","point":{"x":1000,"y":0},"attachment":"end"},{"wallId":"wall-b","edge":"drawn","point":{"x":1000,"y":0},"attachment":"interior"}]}`. Допустимые `edge`: `drawn`, `opposite`, `startCap`, `endCap`; `attachment`: `end`, `interior`. Точка каждого участника кратна 0,1 мм и лежит на указанной физической грани после квантования. В одном стыке два или более уникальных `wallId`; несколько стен в одном месте объединяются одной записью. Стабильный `id` сохраняется при допустимой правке, а грани и точки пересчитываются. Невозможность восстановить контакт отклоняет команду целиком. Перекрытие полигонов допускается лишь для стен, участвующих в одном зарегистрированном стыке, **в локальной области этого контакта**. Для `drawWall` она ограничена коротким торцом новой стены в месте первого контакта, его продолжением внутрь принимающей стены и противоположной физической гранью принимающей стены: пересечение должно быть связным и целиком лежать в полосе, которую заметает этот торец по направлению построения до противоположной грани. Если направление новой стены параллельно принимающей грани, положительное продольное перекрытие не является таким контактом. Выход за эту полосу более чем на 0,1 мм, проход сквозь противоположную грань или вторая отдельная область пересечения отклоняются даже при общем `junctionId`. Допустимая площадь объединения учитывается однократно.

`setWallThickness(wallId, thicknessMm)` сохраняет `drawnEdge`, регенерирует два противоположных угла и пересчитывает физические контакты и комнаты. Допустимая толщина, сделавшая полезную комнату пустой или многокомпонентной, применяется; комната получает `polygon: null`, `areaMm2: null` и причину, а раскладка для неё недоступна. `nudgeWallHandle(wallId, handle: start | center | end, axis: x | y, direction: -1 | 1)` сдвигает выбранный край на 1 мм, регенерирует четыре угла и связанные стены. Крайние точки удерживают неподвижные внутренние контакты или вся команда отклоняется; средняя переносит всю стену и её внутренние контакты, меняя только присоединённые концы соседей. `deletion-preview` оценивает удаление физической стены по тому же графу.

Сервер хранит физические контакты концов и внутренних Т-стыков по `wallId` и месту встречи границ. Он останавливает создаваемую стену у **первой физической грани** препятствия, а не у оси, и допускает пересечение занятых областей только как часть зарегистрированного стыка. `wallArea` — объединение физических четырёхугольников с непрерывным внешним контуром без внутренних швов; предпросмотр допустимой команды использует ту же функцию геометрии, что и принятый результат. Выделение отдельной стены использует её `corners`, а не общий `wallArea`.

`preview` принимает текущий физический граф, `basisKey` и те же `drawnEdge`/`side`/`thicknessMm`, что `drawWall`, но не создаёт ревизию и не сохраняет стену. Он возвращает канонический предложенный край, четыре угла новой стены, объединённый предпросмотр `wallArea`, допустимость и причину. Ответ помечен исходным `basisKey` и идентификатором запроса; клиент отбрасывает устаревшие ответы после движения указателя, смены стороны/толщины или изменения графа. На время ожидания последнего ответа можно показывать только незакреплённый локальный четырёхугольник без обещания допустимого стыка.

Первый рабочий этап построения включает зарегистрированный бесшовный Г-/Т-стык **двух** стен и одинаковый preview/commit. Наклонные и многостенные контакты, перенос стыка и перерасчёт полезной комнаты дополняют тот же контракт на следующем этапе; итоговое поведение для всех допустимых стыков одинаково. Ответ `validate` для сохранённой стены не зависит от наличия команды создания в текущем этапе реализации.

Ответ v5 содержит `schemaVersion: 5`, `status: applied | invalid`, `graph`, `affectedWallIds`, `wallArea`, `faces`, `openJointAngles`, `issues`, `basisKey` и новую ревизию при применении. `faces[].polygon` есть полезный физический контур, `areaMm2` — площадь в мм², `innerAngles` и `freeDimensions` — измерения по внутренним граням вне стены. `faces[].topologyKey` зависит от инцидентности стен/контактов, а `geometryKey` — от фактического полезного контура, поэтому изменение толщины может сохранить комнату и одновременно сделать прежнюю раскладку устаревшей. Угол открытого стыка возвращается отдельно от `faces[].innerAngles` как `openJointAngles[]` с `junctionId`, `wallId`, `adjacentWallId`, `valueDeg` от 0° до 180°, `label: «Угол стыка»` и якорем дуги/подписи в свободной области. Для каждой примыкающей стены своя запись; подписи разнесены при нескольких ветвях. Непригодная комната возвращает `polygon: null`, `areaMm2: null` и причину.

Локальный клиент этой версии хранит только `ProjectDocumentV6` в `plitka-projects-v6`. После успешной записи и проверки нового каталога либо проверки уже существующего валидного v6 под блокировкой удаляются все ключи v1–v5, включая прежние проекты с точностью 0,1 мм. Очистка возобновляется при каждом запуске и не удаляет валидный v6. Импорт файлов старой схемы отклоняется; отсутствие или ошибка записи v6 не разрешает удалять прежние ключи. Все вложенные графы, включая Undo, restore и confirmed, используют `PhysicalGraphV5`.

При `invalid` ответ возвращает исходный граф целиком; ни один угол стены, контакт, комната или ревизия не меняется. `commandId`, `basisKey` и CAS-ревизия сохраняют идемпотентность и защиту от устаревшего запроса. Пользовательский текст `issues[].message` не содержит координат или списков вершин. Предметные числа имеют не более одного десятичного знака; служебные ключи/ревизии не квантуются. `/api/v5/layout` и `/api/v5/optimize` получают новый `faces[].polygon` без смены своей версии и единиц.

## Геометрия v4 — совместимость предыдущего релиза

Существующий `POST /api/plan/command` принимает граф v4, команду, `basisKey`, `commandId` и сведения о ревизии; возвращает граф, статус, проблемы, область стен и производные комнаты. Единицы координат и толщины — мм. Текущие `drawWall` и `setWallThickness` сохраняют прежние поля и смысл.

## Новая команда

```json
{
  "type": "nudgeWallHandle",
  "chainId": "wall-chain-id",
  "handle": "start",
  "axis": "x",
  "direction": 1
}
```

`handle` допускает `start`, `center`, `end`; `axis` — `x` или `y`; `direction` — `-1` или `1`. Один вызов смещает выбранную точку ровно на 1 мм по указанной оси; произвольный `deltaMm` клиент не задаёт. `chainId` указывает на WallChain, а не на отдельный Segment, потому что стыки делят одну стену на несколько сегментов. Неизвестная цепь, неверная форма или значение поля отклоняются существующим способом проверки запроса.

Для `start`/`end` сервер меняет только соответствующую крайнюю вершину цепи на 1 мм. Все внутренние вершины и противоположный конец остаются на месте; если через неподвижные внутренние вершины новая ось не может остаться прямой и упорядоченной, сервер отклоняет всю команду. Для `center` сервер переносит все вершины выбранной цепи на 1 мм, включая внутренние стыки. Разделяемые вершины стыков остаются едиными ID; присоединённые стены меняют положение своих затронутых концов, а их дальние концы остаются на месте. Если любая присоединённая цепь не может остаться валидной, сервер отклоняет всю команду, не искажая её молча.

Перед `status: applied` обязательны проверка порядка и положительной длины сегментов, прямолинейности всех цепей, топологии, ограничений, пересечений, совпадения вершин и физического наложения всех затронутых стен. Ответ `affectedChainIds` содержит каждую стену, координаты которой изменились, включая присоединённые через общий стык. На невозможное изменение сервер возвращает `status: invalid`, исходный `graph` и понятную причину в `issues`. Пользовательский `issues[].message` не содержит числовых координат и списков вершин; код проблемы и структурированные идентификаторы могут сохраняться для проверки и выбора на полотне. Например, `coincident_vertices` объясняет совпадение точек стены без пары X/Y. Никакой части смещения не сохраняется. Клиент не оставляет блокирующее `pendingEdit` после такого ответа и допускает следующую стрелку. Повторный `commandId` сохраняет существующую идемпотентность; проверка ревизии и `basisKey` действует как для других команд.

## Существующая физическая стена

`drawWall` принимает осевую линию и толщину новой стены (по умолчанию 100 мм). Ось доходит до топологического стыка с первой встреченной стеной; видимая новая область подрезана у первой физической грани. Область всех стен — объединение, поэтому стык считается один раз. Продолжение через стену или недопустимое наложение отвергается атомарно. `setWallThickness` меняет толщину цепи; допустимая толщина, сделавшая полезный контур комнаты непригодным, всё равно применяется, а комната получает причину невалидности и блокировку расчёта плитки.

Ответ сохраняет `graph.chains[].thicknessMm`, объединённую `wallArea`, `faces[].axisPolygon`, полезный `faces[].polygon`, `areaMm2`, `dependencyKey`, `geometryKey` и `validation`. Непригодный полезный контур возвращает `polygon: null`, `areaMm2: null` и причину, без выбора одного из нескольких компонентов. Идентичность комнаты определяется осевым контуром и не меняется от одной только толщины.

## Числовой контракт

Версия ответа геометрического API остаётся `schemaVersion: 4` и не совпадает с версией локального документа v5. Во входной команде предметные параметры (координаты, толщина, длина, угол) имеют шаг 0,1 мм или 0,1° по смыслу поля; значения с большей точностью отклоняются. Служебные идентификаторы и целочисленные ревизии не квантуются.

Сервер может вычислять пересечения и решать ограничения с более высокой промежуточной точностью. Перед формированием ответа новые общие вершины согласованно приводятся к десятичной сетке 0,1 мм. Клиент выбирает цель перпендикулярной направляющей как ближайшую каноническую точку к идеальной до отправки команды: отклонение от неё не более 0,08 мм, от соответствующей 100-миллиметровой отметки не более 0,1 мм, от прямого угла не более 0,1°. Сервер применяет к полученной точке обычную проверку команды и после приведения повторяет проверки стыков, порядка и прямолинейности цепей, размерных условий, коллизий и физического наложения. Производные полигоны, измерения, площади и ключи зависимостей формируются из итогового графа, а предметные числовые поля ответа имеют не более одного десятичного знака в своих единицах; `areaMm2` выражено в мм². Ключи остаются детерминированными для повторной команды. Если правка невалидна после приведения, сервер возвращает `status: invalid`, исходный граф и причину; частичного результата нет.

## Локальный проект

В каталоге `plitka-projects-v5` хранятся только новые документы `schemaVersion: 5`, прошедшие проверку числового инварианта во всех вложенных снимках графа и комнатах. При первом создании v5-каталога приложение удаляет прежние ключи v1–v4 и не переносит их проекты. Каждый последующий запуск повторяет удаление оставшихся старых ключей под блокировкой, не очищая валидный v5. Форматы файлов v1–v4 не импортируются; изменение этой политики потребует отдельного решения пользователя. Отказ записи нового каталога не удаляет старые данные.
