# Contract: Граф плана с физическими стенами

Этот контракт расширяет существующие `POST /api/plan/validate`, `POST /api/plan/command` и `POST /api/plan/deletion-preview`. Нового endpoint нет. Схема запроса и ответа графа меняется с `schemaVersion: 3` на `4`; старый запрос получает существующий ответ `invalid_request` (422), а не молчаливое присвоение толщины. Документ проекта v4 описан в [data-model.md](../data-model.md).

## Входной граф

`graph.chains[]` обязательно содержит положительное конечное `thicknessMm` в миллиметрах для каждой цепи. `segments[]` сохраняют ссылки на `chainId`, но не дублируют толщину. Поле обязательно во всех вложенных графах документа; отсутствие поля отклоняется строгим парсером. Число 100 мм является начальной настройкой инструмента и передаётся при создании, а не подставляется при чтении старого графа.

## Команды `POST /api/plan/command`

| Команда | Поля помимо общих `schemaVersion`, `commandId`, `draftRevision`, `basisKey`, `graph` | Результат |
| --- | --- | --- |
| `drawWall` | `start: {x,y}`, `end: {x,y}`, `thicknessMm` | создаёт осевую цепь и нужные вершины/стыки; при препятствии ось доходит до топологического стыка, а видимая добавленная область — только до первой физической грани |
| `setWallThickness` | `chainId`, `thicknessMm` | меняет толщину одной цепи, пересчитывает физические области и затронутые комнаты; если полезный контур комнаты исчезает, команда возвращает `status: applied` с новой толщиной и невалидной комнатой, а расчёт блокируется |
| `connect` | прежние `fromVertexId`/`to` и `thicknessMm` для создаваемой цепи | сохраняет существующее соединение; при split существующая цепь наследует свою толщину |
| `addTemplate` | прежние поля и `thicknessMm` | все новые цепи шаблона получают переданную толщину |

Координаты, толщина и ссылки проверяются сервером. Для `drawWall` сервер определяет первый контакт вдоль проведённого отрезка и при Т-стыке создаёт топологическую связь осей с существующей стеной. Локальный предпросмотр показывает полосу новой стены до первого препятствия за вычетом уже занятой области: видимый вклад заканчивается ровно у первой физической грани без зазора. Невидимая часть осевой связи внутри занятой области нужна только для топологии. После команды `wallArea` является объединением полных физических областей цепей, не зависит от порядка их создания и считает площадь стыка один раз; отдельный видимый вклад цепи не сохраняется. Продолжение за первой стеной, параллельная накладка и невозможный стык не применяются. Команда атомарна: `status: invalid` возвращает исходный `graph` и причину в `issues`; UI показывает ошибку. Отмена предпросмотра не отправляет команду. Условия размеров существующих осевых линий сохраняют прежний смысл.

## Производные поля ответа

| Поле | Смысл |
| --- | --- |
| `graph.chains[].thicknessMm` | сохранённая толщина соответствующей стены |
| `wallArea: PolygonData[]` | единая физическая область стен, разбитая на компоненты для рисования заполненных SVG-фигур; стыки уже объединены |
| `faces[].axisPolygon` | осевой контур для устойчивой идентичности комнаты и размерных условий |
| `faces[].polygon: PolygonData \| null` | единый полезный контур за вычетом физической области стен; `null`, если результат пуст или распался на части |
| `faces[].areaMm2: number \| null` | площадь пригодного контура; `null` одновременно с `polygon: null` |
| `faces[].dependencyKey` | меняется при изменении толщины любой зависимой цепи |
| `faces[].geometryKey` | меняется при изменении полезного контура; прежний результат плитки становится неактуальным |

`topologyKey` и ссылки `outer`/`holes` сохраняют идентичность по осевым цепям. Если полезный контур пуст или распался на несколько областей, `faces[].polygon` и `areaMm2` равны `null`, `faces[].validation.valid` равно `false`, а `issues` содержит объяснимую причину; нельзя выбирать один компонент молча. Если единый контур нарушает лимиты планировщика, контур и площадь остаются в ответе, но `validation.valid` равно `false`. Во всех невалидных случаях подбор плитки блокируется.

Для принятой команды `setWallThickness` общий `GraphResponse.status` равен `applied` даже при `faces[].validation.valid: false`: ответ содержит изменённый `graph`, невалидное помещение и причину в `issues`, а клиент сохраняет новый черновик и делает прежнюю раскладку неактуальной. `status: invalid` означает отказ самой команды: ответ содержит исходный `graph`, а клиент не сохраняет изменение толщины.

## Ошибки и совместимость

- Отсутствующая, нечисловая или неположительная толщина не изменяет граф: некорректный запрос отклоняется как 422. Невозможный стык либо физическое наложение без допустимой связи возвращает `status: invalid` и исходный граф. Положительная толщина, из-за которой исчезает полезная площадь комнаты, возвращает `status: applied`, изменённый граф, невалидную комнату и объяснимый `issue`; подбор плитки для неё блокируется.
- Одновременные правки сохраняют существующие проверки ревизии, `basisKey` и `commandId`; повтор команды не должен создавать вторую стену.
- Все пути сборки графа — ручное соединение, шаблон, split, delete, Undo, восстановление и подтверждённые комнаты — обязаны сохранять толщину. Старые v1–v3 документы и импортируемые файлы не преобразуются в v4.
