## Dependencies & Execution Order

```text
Setup T001–T002 → Foundation T003–T015 → US1 T016–T018 → US2 T019–T027 → US4 T028–T042 → US3 T043–T046 → Polish T047–T049
```

- Фундамент T003–T015 обязателен перед первой сквозной v6-проверкой: T003/T004 независимы; T006→T008 формируют сохранение, T012→T014 подключают новый API, T015 проверяет их вместе. US1 не открывает физический проект через старый v4-маршрут.
- US1 можно завершить на сохранённой физической стене благодаря `validate` из T012, отдельно от новой команды построения. US2 даёт стену и обычный физический стык двух стен как первый MVP, с запретом длинного перекрытия уже на этом этапе; US4 расширяет тот же алгоритм для наклонных и многостенных стыков, комнат и расчёта; US3 проверяет доступность общей модели.
- В каждой истории проверки стоят до реализации; задачи с общим исходным файлом исполняются последовательно. Отказ `invalid` и совместимость старого маршрута проверяются на каждом соответствующем рубеже.
- Polish начинается после всех историй. Ни локальные проекты v1–v5, ни новый v6 не мигрируют друг в друга: старые удаляются только после работоспособного каталога v6.

## Implementation Strategy

1. Закончить Foundation и проверить пустой v6-документ и сохранённую физическую стену через новый API; это обязательное условие любого последующего сквозного сценария.

3. Добавить US4: сложные физические стыки, полезные комнаты, «Угол стыка», атомарные правки и расчёт по внутреннему контуру. Проверить старую и новую единицу площади.
4. Завершить US3 и общую проверку. Старые `/api/plan/*` обслуживают уже открытые вкладки; каталог v6 сохраняет только новые проекты после удаления v1–v5.
